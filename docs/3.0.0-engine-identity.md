# BloxMiner 3.0.0 — engine identity proofs

Both engines are rebuilt for 3.0.0. This document states exactly which binaries were built, which were
compared against which, how, and what the result was — no "byte-identical engines" shorthand.

## Verus engine

**Source change**: `configure.ac`'s `AC_INIT` release number, `2.1.0` → `3.0.0`. That one line is the
entire diff between `build/bloxminer.patch` and the 2.1.0 patch it supersedes (verified: applying the new
patch to a pristine upstream checkout reproduces the patched tree exactly, `diff -rq` empty).

**Built**: same chroot, same `build/build.sh`, same flags as the 2.1.0 release (Ubuntu 22.04 LTS,
clang 14.0.0-1ubuntu1.1, `-march=x86-64-v3 -mtune=znver3 -maes -mpclmul -fno-strict-aliasing -O3`).
Reproducible: two independent runs from the same chroot both produced sha256
`d630fd356fe8ed85178ab9027d30c8a736eba2052265bd206fd143035eb83c79`.

| | 2.1.0 binary | 3.0.0 binary |
|---|---|---|
| sha256 | `3fd67be21d82c3fb62249fd612c1bbaea6743c21146340a489294d567acf0a88` | `d630fd356fe8ed85178ab9027d30c8a736eba2052265bd206fd143035eb83c79` |

**Proof**: `tools/hashing-identity.sh` compares these two binaries directly — every function whose name
matches `verus|haraka|clhash|scanhash` is disassembled and compared after normalising only what depends on
link-time placement (RIP-relative displacements, absolute branch/call targets). Result: **15/15 hashing
functions instruction-identical**. `libomp.so.5` from this build: sha256
`0387cd34848772e4a9558f562a54791863459b5e6b187d77641be1519388d5d3` — identical to 2.1.0's. `cli_test.sh`
36/36 and `stratum_fuzz.py` 57/57 pass on the new binary, release and ASan/UBSan sanitizer builds both.

## RandomX engine

**Source change**: `build/branding.patch` (applied after `build/donate0.patch`) adds one new header,
`src/version_blox.h` (`BLOX_DISPLAY_VERSION "3.0.0"`), and touches exactly two existing files:
`src/base/kernel/config/BaseConfig.cpp` (one new startup-summary log line) and `src/core/Miner.cpp` (a
literal prefix on the existing periodic hashrate log line). `APP_NAME`/`APP_VERSION`/the mining user-agent/
the JSON API's `version` field are untouched — confirmed by the patch's own diff and by the object-level
proof below.

**Built**: same pinned environment as the RandomX engine's previous internal build (an unreleased 1.0.0 build,
informally called "BloxMiner-X" during development — never separately published) — root, Ubuntu 22.04 LTS
chroot, gcc 11.4.0-1ubuntu1~22.04.3 / g++ 11.4.0, cmake 3.22.1, static libuv 1.51.0 / hwloc 2.12.1 / OpenSSL
3.0.16 (pinned dep hashes unchanged from that build's `build-rx.sh`). `build/build-rx.sh` run twice
independently reproduces the same shipping binary sha256 both times.

| Binary | What it is | sha256 |
|---|---|---|
| Previous internal build (1.0.0, never published) | donate0.patch only, original build | `721aa3fc9a7a23f956e56e86208e2c8adc5cfb0b12df474fdc66063709e356ac` |
| "nobrand" reproduction | donate0.patch only, rebuilt **with the exact `build/build-rx.sh` recipe/toolchain used for the 3.0.0 shipping binary** (temporarily removing `branding.patch`'s effect only) | `721aa3fc9a7a23f956e56e86208e2c8adc5cfb0b12df474fdc66063709e356ac` |
| **BloxMiner 3.0.0 shipping binary** | donate0.patch + branding.patch, via `build/build-rx.sh` unmodified | `44cff475d5813c66daacfbc6079775f2031d2dc81ec12c8a04c8bcb39fc9d6c1` |

**X6 carry-over bridge**: the "nobrand" reproduction — built with the *same recipe, same toolchain, same
chroot* that produces the actual 3.0.0 shipping binary — is **bit-for-bit identical** to the previous
internal build that was originally benchmarked (the X6 gate). This is stronger than "equivalent": it is the
same bytes. The historical X6 evidence (+0.106% vs stock xmrig-new, measured on that earlier binary) remains
relevant because the mining objects are unchanged; 3.0.0 adds logging changes and received its own separate
ABBA sanity check (see BENCHMARKS.md).

**Object-level proof that only the two touched files changed**: both binaries above (the "nobrand"
reproduction and the actual 3.0.0 shipping binary) were built back-to-back from the *same*
`build/build-rx.sh` invocation shape (same chroot, same toolchain, same static-dependency recipe,
same pinned commit `b2ca72480c58d197e18c885d9fc1a0c8d517e60a`), keeping each run's intermediate CMake
build directory (normally deleted on exit) instead of discarding it, and comparing every resulting
`.o` file by sha256:

- **208 of 210 object files byte-identical.**
- The only two that differ: `CMakeFiles/xmrig.dir/src/base/kernel/config/BaseConfig.cpp.o` and
  `CMakeFiles/xmrig.dir/src/core/Miner.cpp.o` — exactly the two source files `branding.patch` touches.
- Every RandomX, crypto, JIT-compiler and backend/cpu object is in the untouched 208.

(An earlier attempt at this same comparison, using a throwaway script that rebuilt the static dependencies
— libuv/hwloc/OpenSSL — without the same `-O2 -ffile-prefix-map=...` flags as `build/build-rx.sh`'s real
recipe, produced two xmrig binaries that matched *each other* but did not match the actual shipping binary
or the previous internal build. That comparison was toolchain-mismatched and has been superseded by the
one above, which uses the real build script unmodified.)

**Functional proof**: `xmrig --bench=1M -t 24`, RandomX `ryzen_19h` MSR preset, 100% huge pages —
**identical result hash on both binaries**: `898B6E0431C28A6B` (shipping binary: 115.9s, 8626.1 h/s;
"nobrand" reproduction: 115.5s, 8654.8 h/s — timing varies with system load; the hash proves the
computation itself is unchanged). Captured screen output of the shipping binary confirms the two new
branding lines render as designed:

```
 * BLOXMINER    3.0.0 (XMRig 6.26.0 engine)
...
BloxMiner 3.0.0  miner    speed 10s/60s/15m 8869.8 n/a n/a H/s max 9061.2 H/s
```

bloxsense (unrelated to this patch): sha256 `8a1265a5da9fc5a04a20de32efae5599e4da43bf5169015d16c52f66d1616f30`,
unchanged — its source was never touched.

## Packaging

`bloxminer-3.0.0.tar.gz` (this release) embeds the Verus binary `d630fd35…` and the RandomX binary
`44cff475…` documented above — both are exactly the binaries these proofs cover, not a later or earlier
rebuild. `build/package.sh` verifies both against their own build provenance (sha256, patch hashes,
declared version) before assembling the package; see `build.provenance` inside the package for the full
machine-readable record.
